# 株レポート修繕パック 設計書（2026-06-29）

## 背景・目的

朝夜の株レポート＋監視銘柄DBの自動化パイプラインは完成済みだが、運用の中で
「気づきにくいが実害のある」5つの弱点が確認された。本パックはそれらの修繕のみを
スコープとする（機能追加はスコープ外）。

## スコープ外（今回やらない）

- 配当カレンダー・NISA枠管理・週次まとめ・セクター分散（パックB）
- 株主優待の手動調査・watchlist.csvの廃止整理（パックC）

## 修繕項目

### A1. 発掘銘柄の採用案内の誤りを修正

- **問題**: 朝レポートの💎発掘銘柄セクションが「watchlist.csv に追記」と案内しているが、
  銘柄リストの正はNotionの「📋 監視銘柄リスト」DBに移行済み。案内どおりCSVを編集しても
  反映されない（Notion DBが優先されるため）。
- **修正**: 案内文を「📋 監視銘柄リストで＋New → コード・銘柄名・区分=監視 を入力」に変更。
- **対象**: `daily_report.py` の発掘銘柄セクション（1箇所の文言）。

### A2. 差分スナップショットのクラウド永続化

- **問題**: `last_snapshot.json`（前回シグナル）と `last_discovery.json`（発掘の顔ぶれ履歴）が
  gitignore かつクラウド実行はレポジトリを毎回まっさらにcheckoutするため、GitHub Actions上では
  常に「前回なし」。→「前回からの変化」が毎回「変化なし」、発掘の重複回避も効かない。
- **修正**:
  1. 両ファイルを `.gitignore` から除外し、リポジトリにコミットして状態を運搬する。
  2. `daily_report.yml` に `permissions: contents: write` を付与。
  3. レポート実行後に両ファイルを自動コミット＆pushするステップを追加
     （変更がない場合はスキップ。ワークフローはschedule/dispatch起動のみなのでpushによる
     再帰起動は発生しない）。
- **検証**: ローカルで2回連続実行し「前回からの変化」に差分が出ること。クラウドは夜19時の
  実行後にコミットが積まれ、翌朝レポートに変化欄が出ることで最終確認。

### A3. 監視銘柄DBの「判定」をレポートと同一基準に

- **問題**: 30分毎の `refresh_watchlist.py` は価格情報のみで判定を計算するため、
  レポート側では⛔判断保留（例:ベリテ=減配）でも、DBの判定列には出ない。基準の不一致。
- **方針**: 30分毎に46銘柄のニュースを取得する方式は採らない（Google Newsへの負荷・
  実行時間・ブロックリスクのため）。代わりに:
  1. 監視銘柄DBに `ニュースフラグ`（rich_text）列を追加。
  2. 朝夜レポートの `collect_portfolio` 実行後、検出したリスク/好材料フラグ
     （例: `減配` / `増配・自社株買い`）を各銘柄のDB行へ書き戻す（フラグなしは空文字で上書き）。
     書き戻しのため `load_watchlist_from_notion` はコード→ページIDの対応も保持する。
  3. `refresh_watchlist.py` は `ニュースフラグ` 列を読み、`trade_signal` に渡す。
     フラグは「・」区切りの語（例: `減配・引当金計上`）として保存し、refresh側は各語を
     `NEWS_RISK` / `NEWS_POSITIVE` の定義値と照合してリスク/好材料に振り分ける
     （独自フォーマットを発明せず、既存の分類辞書を正とする）。
- **性質**: ニュースフラグの鮮度は「直近の朝夜レポート時点」となる（最大約半日遅れ）。
  30分毎の価格更新と組み合わせ、判定は「最新価格×直近レポートのニュース」で算出される。
- **検証**: レポート実行→DBのベリテ行に `減配` フラグ→refresh実行→判定が⛔になること。

### A4. 祝日判定の自動化

- **問題**: `TSE_HOLIDAYS` が2026-2027年の手打ちリストで、2028年以降は休場判定が切れる。
- **修正**: `jpholiday` ライブラリで祝日判定し、年末年始（12/31〜1/3）はルールで補完。
  `jpholiday` が import できない環境では既存の手打ちリストにフォールバック。
  両ワークフローの pip install に `jpholiday` を追加。
- **検証**: 2026の祝日（5/6振替等）・土日・平日・2028年の祝日（自動判定）でユニット的に確認。

### A5. AI出力の文字化けガード

- **問題**: Groq(llama)の生成文にまれに非日本語圏の文字（アラビア文字等）が混入する。
- **修正**: `clean_ai_text()` を新設し、日本語・英数・記号以外のスクリプト
  （アラビア・ヘブライ・デーヴァナーガリー・タイ・ハングル等）を除去。
  すべてのGroq呼び出しの戻り値に適用。各プロンプトに「出力は日本語のみ」を明記。
- **注意**: ニュース見出し等の取得データには適用しない（AI生成文のみ）。

## エラーハンドリング方針

既存のフォールバック構造（Notion DB→CSV→既定リスト、分足→日足、リトライ）は維持。
新規要素はすべて「失敗しても本体の生成を止めない」best-effort とする
（フラグ書き戻し失敗＝ログのみ、jpholiday不在＝手打ちリスト、コミット失敗＝レポート自体は完了済み）。
